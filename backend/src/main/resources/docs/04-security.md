# 安全评估：32 个指标在看什么

站内每个 Skill 都会被扫一遍，得到一个 **0-100 的风险分**和一个 **四档等级**。

这套口径对齐 openEuler SkillHub 的评估规范（指标源自 SkillSpector 的规则族）。
它是**纯本地、确定性、可解释**的：同一份文本，永远得到同一个结果。

## 1. 四档等级

| 等级 | 分数区间 | 意思 | 建议动作 |
| --- | --- | --- | --- |
| 安全 `safe` | 0 - 20 | 没发现可疑行为 | 直接用，用前扫一眼正文 |
| 低风险 `low` | 21 - 50 | 有一些常见的工具调用写法 | 确认它访问了哪些外部服务 |
| 中风险 `medium` | 51 - 80 | 会读写文件 / 执行命令 / 访问网络 | 先在隔离环境试跑 |
| 高风险 `high` | 81 - 100 | 有高危特征（远程下载执行、提权、读凭据） | 不要在产线直接用 |
| 未检测 `unrated` | — | 没有评估记录 | 点「重新评估」 |

## 2. 六个维度

| 维度 | 看什么 |
| --- | --- |
| **提示注入** | 指令覆盖、隐藏指令、隐性指令、上下文填充 |
| **数据外泄** | 向外部地址发数据、读环境变量里的密钥、读凭据文件、访问 Agent/MCP 配置、枚举其它 Skill |
| **权限与代码执行** | sudo、子进程、shell 直接执行、不安全的工具参数/默认配置、无约束工具授权、高风险自动决策、能力超范围、无上限资源消耗 |
| **供应链风险** | 依赖未锁版本、远程下载并执行、依赖有已知漏洞、恶意样本特征、攻击工具特征 |
| **系统提示与记忆** | 系统提示泄露、记忆投毒、输出未校验、未校验输出拼进 SQL/命令、未声明权限范围 |
| **危险代码** | 运行时自我修改、建立持久化驻留 |

## 3. 分数怎么算

```
风险分 = min(100, Σ 命中指标的权重)
```

- 每条指标有固定权重（8 ~ 36 分），命中即计入，同一指标**只计一次**。
- 同一指标最多记录 5 处命中位置，全部明细合计最多 40 条。
- 分数封顶 100，不会因为"命中很多"而超过 100。
- 等级由分数换算，区间固定。

**为什么用加权而不是计数**：命中 1 条"远程下载并执行"（34 分）比命中 4 条"依赖未锁版本"（8 分 ×4 = 32 分）更值得警惕。

## 4. 一条结构性规则

大部分指标是**正则匹配**，只有一条是**结构性判断**：

> **LP3 · 未声明权限范围**（12 分）：
> 如果 `SKILL.md` 里既没有 `allowed-tools` 也没有 `permissions:` 之类声明，
> 就说明作者没告诉读者"这个 Skill 会用到哪些能力"，记 12 分。

补上声明就自动消失。

## 5. 在线试算

「安全评估」页有一个输入框，粘贴任意文本即可算出分数。
用途：

- 发布前先自查，避免"发出来才发现分数很高"
- 理解某条规则到底在匹配什么

试算结果与正式评估走的是同一套引擎，因此两者分数一致。

## 6. 三条重要澄清

1. **分数高 ≠ 恶意**。一个"帮你跑测试"的 Skill 一定会执行命令，分数注定不会低。
   评估的作用是让人知道风险，不是替人做决定。
2. **分数低 ≠ 无害**。规则库是有限的，覆盖不到的写法就是覆盖不到。
   评估是**第一道筛子**，不是最后一道。
3. **本站不做动态分析**。它不运行 Skill、不联网、不调模型。
   要看"这个 Skill 实际会做什么"，请用标准版 StanSkillHub 的在线实测。

## 7. 我要降分，怎么做

每条命中信号都带一个 `remediation`（修复建议），直接照着改：

| 典型信号 | 常见改法 |
| --- | --- |
| 远程下载并执行 | 改成"下载到本地 → 人工确认 → 再执行"，或在文档里明确这是必要步骤 |
| 读取疑似密钥的环境变量 | 明确写出只读哪几个变量，或改为让用户自己提供 |
| 未声明权限范围 | 在 frontmatter 里补 `allowed-tools` |
| 依赖未锁版本 | 写死版本号 |
| 高风险自动决策 | 改成"给出建议，由人确认" |
