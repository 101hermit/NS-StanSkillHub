## 1. Skill-MS 写门禁（`MsEngine`）

### 1.1 四步固定顺序

```
① 约束裁决 → ② 索引维护 → ③ 事件派发 → ④ 台账落账
```

顺序不可换：
- 约束必须在**落库之前**（否则破坏的数据已经写进去了）；
- 索引维护必须在**写之后**（要用新值算键）；
- 事件必须在**写之后**（要看到最终状态）；
- 台账必须**最后**（要记录前三步的结果）。

### 1.2 约束的七种类型

| 类型 | expression 写法 | 语义 | 示例 |
| --- | --- | --- | --- |
| `NOT_NULL` | 空 | 目标列不能为空 | `name` |
| `UNIQUE` | 空 | 全库唯一（更新时排除自身） | `name` |
| `RANGE` | `min=0,max=80` | 数值区间，可只写一边 | `risk_score` |
| `ENUM` | `published,archived` | 枚举白名单 | `status` |
| `REGEX` | `^[a-z0-9-]+$` | 正则匹配（`find`，不是 `matches`） | `name` 格式 |
| `CHECK_EXPR` | `risk_score<=80` | 单列二元比较，支持 `= != > >= < <=` | 组合规则 |
| `REFERENCE` | `skillset_code->skillset.code` | 引用完整性 | 逻辑库外键 |

判定逻辑在 `ConstraintEvaluator.evaluate(def, row, exclude, judge)`：
- 纯函数，可脱离数据库单测；
- 需要查库的两类（`UNIQUE` / `REFERENCE`）通过 `Judge` 回调注入；
- 表达式写坏（正则编译失败、数字解析失败）时**按通过处理** —— 一条烂配置不该让整个业务瘫痪，
  由「约束」页的「全库校验」把问题暴露出来。

### 1.3 严重度

| severity | 违反时 | 台账 `verdict` |
| --- | --- | --- |
| `ENFORCED` | 抛 422 `MS_CONSTRAINT_VIOLATION`，附约束 code + 具体原因 + 修复建议 | `REJECT` |
| `WARN` | 放行，告警写进台账 `constraint_hits` | `WARN` |

**为什么要有 WARN**：企业推行新规矩时，"先告警一周再强制"是最现实的路径。

### 1.4 约束的作用范围

- `skillset_code = 'default'` 的约束对**所有**逻辑库生效（公共约束）；
- 其它逻辑库的约束只对同库生效；
- `status != 'ACTIVE'` 的约束不参与判定；
- 目标列不在白名单（`name/title/description/category_code/scene_code/tags/version/source/...`）的约束直接跳过 ——
  避免拼错列名导致"看起来配了但永远不触发"。

## 2. 索引（逻辑索引）

| 概念 | 说明 |
| --- | --- |
| 状态机 | `BUILDING`（刚建）→ `READY`（可用）→ `STALE`（底层行变了，条目可能过时）→ `DROPPED`（已删） |
| 条目生成 | 多列用 `\|` 连接：`category_code,scene_code` → `development\|general` |
| 重建 | 清空条目 → 遍历全部 Skill → 按 200 行/批插入 → 置 READY + 写 entry_count |
| 增量维护 | 每次写操作后，对每个 READY 索引追加该行的条目、`entry_count+1`（不做全量重算，代价太高） |
| 命中统计 | 查询计划命中该索引时 `hit_count+1` |

**它和数据库索引的关系**：这是一份"可查询、可解释"的逻辑索引。
MySQL 自己的执行计划仍由它的物理索引决定 —— 本版不尝试干预数据库优化器（那是 DBA 的事）。
标准版的价值是：**让"为什么这个查询快/慢"变成页面上能看到的一句话。**

## 3. 事件（触发器）

| 触发时机 | 何时产生 |
| --- | --- |
| `INSERT` | 新建 Skill（含贡献发布新建） |
| `UPDATE` | 编辑 Skill |
| `STATUS_CHANGE` | 归档 / 恢复 |
| `RISK_HIGH` | 发布时风险等级为 `high`（额外派发一次） |

| 动作 | 效果 |
| --- | --- |
| `TAG` | 把 `action_payload` 追加到 `skill.tags`（已存在则不重复加） |
| `STATUS` | 把 `skill.status` 改成 `action_payload` |
| `AUDIT` / `NOTIFY` / `EVALUATE` | 本版只落 `event_log`（真正的通知/评估需要外部通道，已登记为后续路线） |

**条件表达式**：`condition_expr` 与 `CHECK_EXPR` 同语法（`col op value`），留空表示恒真。

**失败处理**：动作抛异常 → `status=FAILED`、`attempts+1`、记 `last_error`；
`attempts ≥ 3` → `DEAD`。页面上可以对 `FAILED`/`DEAD` 点「重试」（打回 `PENDING`）。

## 4. 查询台（受限 SQL）

### 4.1 语法（白名单）

```
SELECT <cols|*|COUNT(*) [AS n]>
FROM   skills|skillsets|indexes|constraints|events|tx_log
[WHERE cond [AND cond]…]
[ORDER BY col [ASC|DESC]]
[LIMIT n [OFFSET m]]

cond := col (= | != | <> | > | >= | < | <= | LIKE | IN | BETWEEN) value
value := 'str' | number | true | false | (v1,v2,…) | v1 AND v2
```

### 4.2 逻辑表名 → 物理表名

| 页面上的表 | 真实表 |
| --- | --- |
| `skills` | `skill` |
| `skillsets` | `skillset` |
| `indexes` | `ms_index_def` |
| `constraints` | `ms_constraint_def` |
| `events` | `ms_event_def` |
| `tx_log` | `ms_tx_log` |

**为什么要这层映射**：用户想查的是"技能表/索引表"，不是 `ms_index_def` 这种实现名。
映射表保证"页面语言"与"实现"解耦。

### 4.3 三道安全闸

1. **解析器白名单**：表名、列名不在白名单 → 409/2100，`msg` 指出**第几个词**不认识并列出可用列；
2. **模板执行**：SQL 只由固定模板拼接，标识符来自白名单，值一律 `?` 绑定；
3. **只读**：语句必须以 `SELECT` 开头，白名单里没有任何写入口。

## 5. 评估指标与算法（`EvalService` + `Metrics`）

### 5.1 分词

英文按词、中文按**字二元组（bigram）**。理由：不想引词典分词；bigram 对"是否说到了同一件事"
这个粒度够用，且对分词错误不敏感。

### 5.2 九项指标

| 指标 | 维度 | 权重 | 算法 |
| --- | --- | ---: | --- |
| `correctness` 正确性 | 任务效能 | 3 | `F1 = 2·P·R/(P+R)` |
| `coverage` 期望覆盖 | 任务效能 | 2 | 期望的 token 被输出覆盖的比例 |
| `completeness` 内容完整 | 任务效能 | 1 | `min(1, 输出 token 数 / 期望 token 数)` |
| `task_success` 任务完成 | 任务效能 | 2 | 覆盖 ≥0.5 且 F1 ≥0.4 → 1，否则 0 |
| `consistency` 一致性 | 任务效能 | 1 | 重复运行的相似度；单次运行且成功时记 1 |
| `ttft` 首字效率 | 通信性能 | 1 | `1 − min(1, 首字时延/2000ms)` |
| `latency` 时延效率 | 通信性能 | 1 | `1 − min(1, 总时延/30000ms)` |
| `throughput` 吞吐 | 通信性能 | 1 | `tokens/s ÷ 50`，上限 1 |
| `success` 成功率 | 通信性能 | 1 | 调用成功 1 / 失败 0 |

### 5.3 综合分

```
score = Σ(wᵢ × vᵢ) / Σ(wᵢ) × 100      任务效能权重合计 9，通信性能合计 4
```

任务效能占约 **69%** 的权重 —— 先看答得对不对，再看快不快。

### 5.4 TOPSIS 排名

对"有实测记录"的 Skill，准则为 `[均分(权重3), 实测次数归一(权重1)]`：
① 向量归一化 → ② 乘权重 → ③ 求正/负理想解 → ④ 算相对贴近度。
**好处**：把"又高又稳"和"偶尔很高但样本少"区分开。

## 6. 不变量（写代码时的红线）

| # | 不变量 | 守护位置 |
| --- | --- | --- |
| I1 | 所有 Skill 写操作都经过 `MsEngine` | 评审清单 + 事务台账（漏调就查不到台账） |
| I2 | 约束判定发生在落库之前 | `beforeWrite` 在 `updateSelective` 之前调用 |
| I3 | 事件日志与业务写同事务，动作不在事务内 | `afterWrite` 的 try/catch 结构 |
| I4 | 查询台的用户输入永不进标识符位置 | 解析器白名单 + `safeIdent` 二次校验 |
| I5 | 指标口径只有一处真源 | `EvalService.SPECS`（字典与打分都读它） |
| I6 | `eval_run.score_total` 先写 0 再回写（NOT NULL 列） | `run()` 里的两段式写入 |
| I7 | 离线兜底必须在结果里显式标注 | `AgentPort.Reply.offline` → 页面徽标 |
