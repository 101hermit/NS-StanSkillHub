# SSKH 01 · 需求与定位

## 1. 一句话定位

**把 Skill 库当成一个数据库来管。** 在简易版（资源站）的全部能力之上，增加
**库语义**（逻辑库 / 索引 / 约束 / 事件 / 事务台账 / 查询台）与
**单点在线实测 + 统计口径的质量评估**。

共享基线见仓库根 [docs/00](../../docs/00-三系统总纲与递进设计.md) 起 8 篇；本文只写标准版的增量。

## 2. 为什么需要标准版

简易版解决"有没有、在哪、怎么装"。但当一家企业把 Skill 用到 **300 个以上**时，
新的问题全是**库语义问题**：

| 真实痛点 | 属于哪类数据库问题 | 标准版的答案 |
| --- | --- | --- |
| 谁在维护这 300 个？哪些是研发的、哪些是市场的？ | 库 / 表空间划分 | **逻辑库 Skillset** |
| 改一个 Skill 会不会踩到别人的约定？ | 约束 | **7 类约束 + ENFORCED/WARN** |
| 某个字段天天用来筛，为什么还这么慢？ | 索引 | **索引 + 查询计划** |
| 新增 Skill 之后要记得做的三件事，总有人忘 | 触发器 | **事件（含重试与死信）** |
| 出问题要查"上次谁改的、为什么放行" | 审计 / redo | **事务台账 `ms_tx_log`** |
| 我想像查数据库一样查一下 | SQL | **受限 SQL 查询台** |
| 这个 Skill 挂到模型上到底行不行？ | 集成测试 | **单点实测 + 指标评分** |

**一句话判据**：标准版的每一个写操作都能回答"被哪条约束放行、动了哪些索引、触发了哪些事件"。

## 3. 干系人

| 角色 | 在意什么 | 标准版怎么满足 |
| --- | --- | --- |
| **库管理员**（DBA 式角色） | 库结构清晰、改动可控、可解释 | 逻辑库 / 索引 / 约束 / 事件 + 事务台账 |
| **Skill 作者** | 我改的东西不会被莫名其妙的规则挡住 | 拦截时给出约束 code + 具体原因 + 修复建议 |
| **评测者** | 这个 Skill 挂到模型上到底行不行 | 单点实测：输出 + 推理过程 + 9 项指标 |
| **平台工程师** | 接入要能自己排查 | 接入管理：注册 / 探活 / 一键体检 / 出网自述 |

## 4. 需求清单

### 4.1 必须（P0，全部已验证）

| # | 需求 | 判据 |
| --- | --- | --- |
| R1 | 简易版全部 26 个端点与 11 个页面**行为一致** | 40 项用例里前 29 项与简易版完全同名同义 |
| R2 | 逻辑库可建可删；非空库删除被拒并说明原因 | 422 + `MS_CONSTRAINT_VIOLATION` |
| R3 | 索引可建、可重建、可查条目、可删 | `BUILDING→READY`，`entry_count ≈ 375` |
| R4 | 约束 7 类可用，`ENFORCED` 拦截、`WARN` 放行 | 422/2000 与 200 两种结果都验证过 |
| R5 | 事件在写操作后触发并落日志；失败可重试 | `event_log` 有 DONE；死信可 `retry` |
| R6 | 每次写操作落事务台账 | `ms_tx_log` 中能看到约束命中 / 索引 / 事件 |
| R7 | 查询台支持 WHERE/ORDER BY/LIMIT，非法语句指出第几个词错 | 409/2100 + 可用列清单 |
| R8 | 查询计划能说清"用没用索引" | `scan_type=INDEX_SCAN/FULL_SCAN` + `used_index` |
| R9 | 单点实测能返回输出 + 推理过程 + 指标分 | 离线桩下 `status=DONE`、`score_total>0` |
| R10 | 指标字典分任务效能 / 通信性能两维 | 5 + 4 = 9 条 |

### 4.2 应该（P1）

| # | 需求 | 说明 |
| --- | --- | --- |
| R11 | 全库约束校验（不写库，只报告） | `POST /ms/constraints/validate` |
| R12 | 质量汇总 + TOPSIS 排名 | `GET /eval/summary`、`GET /eval/ranking` |
| R13 | Agent / MCP 探活与一键体检 | `POST /agents/{code}/probe`、`GET /conn/doctor` |
| R14 | 出网策略自述（代理 / 根证书 / 直连白名单） | `health.extra` 与「接入管理」页 |

### 4.3 明确不做

- ❌ 知识图谱 / 知识库 / 实体关系 → 专业版
- ❌ 实验矩阵（多 Agent × 多超参）→ 专业版
- ❌ 统计检验 / 聚类 / 回归 → 专业版
- ❌ 分布式、副本、分片、多租户隔离 → 不在本版范围

## 5. 场景剧本

### 场景 A：给"高风险 Skill 不许上架"加一条规矩

1. 「约束」→ 新建：类型 `RANGE`、列 `risk_score`、表达式 `min=0,max=60`、严重度 `ENFORCED`
2. 去编辑一个 84 分的 Skill → 立刻被拦：`422` +「被约束 ck_risk_max 拦截：列 risk_score 是 84，超过上限 60」
3. 「事件」页下方的事务台账能看到这次写操作的 `verdict=REJECT` 与约束命中

### 场景 B：新增 Skill 自动打标签

1. 「事件」→ 新建：触发 `INSERT`、动作 `TAG`、参数 `from-contribution`
2. 去「在线贡献」发布一个新 Skill
3. 该 Skill 的标签里自动多了 `from-contribution`；事件日志一条 `DONE`

### 场景 C：把"按分类查"变快

1. 「查询台」跑 `SELECT name FROM skills WHERE category_code='development' LIMIT 5` → 计划：走了 `idx_cat`
2. 删掉该索引再跑 → 计划变成 `FULL_SCAN`，并提示"给这一列建个索引"

### 场景 D：pdf Skill 到底能不能用

1. 「在线实测」→ 选 `pdf`、Agent `deepseek-flash`、MCP `builtin-calc`、temperature 0.3
2. 输入"把这份 PDF 的第 2-5 页合并成新文件"，期望"给出合并步骤"
3. 得到输出 + 推理过程 + 9 项指标；离线时自动回退离线桩并说明原因
4. 「质量评估」看这个 Skill 的历史均值与 TOPSIS 排名

## 6. 敏捷迭代记录（原型 + 敏捷）

| 迭代 | 目标 | 完成 | 评审后的调整 |
| --- | --- | --- | --- |
| I1 | 库语义骨架：逻辑库 + 索引 | 逻辑库 CRUD、索引建/重建/条目 | 索引重建从"逐行 insert"改为分批（200/批）：375 行 3.2s → 0.4s |
| I2 | 约束引擎 | 7 类约束 + 全库校验 | 发现"唯一约束在更新时会与自己冲突" → 加 `exclude` 参数 |
| I3 | 事件与台账 | 事件 CRUD + 派发日志 + 事务台账 | 动作原设计在业务事务里执行 → 改为「日志同事务、动作在外」，避免外部副作用回滚业务 |
| I4 | 查询台 | 受限 SQL 解析 + 计划 | 原计划支持 JOIN → 砍掉（收益小、注入面大），改为白名单单表 |
| I5 | 在线实测 | Agent/MCP 端口 + 离线桩 + 9 指标 | 原设计无离线兜底 → 断网整页报错；加回退后链路可验证 |
| I6 | 接入管理与出网 | NetEgress（代理 + 动态根证书）+ 体检 | 原来要求手工 keytool → 改为运行时从 PEM 构建 SSLContext |

## 7. 与另两个版本的关系

```
ESKH（资源站 F₀）
  ⊂ SSKH（本版本：F₀ + 库语义 + 单点实测 + 统计口径评估）
      ⊂ PSKH（+ 连通矩阵 + 实验矩阵 + 知识图谱 + 统计检验/聚类/回归/AHP）
```

**本版本必须守住的边界**：
1. 一旦出现"知识图谱"，就说明越界到专业版了；
2. 一旦"实测"开始支持多 Agent 矩阵，就说明越界了；
3. 一旦为了权限而引入完整鉴权体系，就说明偏离了"内网工具"的定位。
